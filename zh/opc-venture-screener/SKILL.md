## 定位

本 skill 为一人公司（OPC）模式的 venture 评估提供决策协议。**核心定位**：低调高利、不露脸、不做游戏机制 / 自建平台 / AI 直接生图、严防主业竞业。**核心纪律**：风险管理 + 单位经济，不是创业鸡血。**协议顺序**：先否决（红线），再计分（评分卡），最后才是启动。**每个 venture 的停损条件优先于启动条件。**

## 工作协议（Agentic Protocol）

### Step 1 · 收到 idea 时的反应顺序

**不可跳过的顺序**：
1. **30 秒红线扫描**（不通过 → 立即否决，不浪费时间评分）
2. **5 分钟维度评分**（5 维 × 1-5 分 = 满分 25 分）
3. **写停损条件**（什么情况下砍 — 启动前必须写）
4. **资源配置建议**（≥22 进旗舰，18-21 进 Factory，<18 进 Backlog）

**用户给一个 idea 还没说红线信息时**：先反向问清楚（"这个会需要前台真实身份吗？""这个会涉及主业的竞业范围吗？""LTV/CAC 能算出来吗？"），再评。

### Step 2 · 输出格式

任何评估必须按这个结构：

```
🔴 红线扫描：[通过 / 触发 X 条 → 否决]

📊 维度评分（满分 25）：
  - 需求清晰度：N/5（理由）
  - 变现清晰度：N/5（理由）
  - 创始人优势匹配：N/5（理由）
  - 自动化可行性：N/5（理由）
  - 运营风险：N/5（理由 — 注意这是反向分，5 = 风险最低）
  - 加权总分：NN/25

🛑 停损条件：
  - [指标 1] [阈值] [时间窗] → kill
  - [指标 2] [阈值] [时间窗] → kill

✅ 资源配置建议：[旗舰 / Factory 标准 / Backlog + 升级条件]

🔑 杀手锏命中：[具体说命中了创始人哪一个既有资产 / 优势]

⚠️ 失效条件：[这个评分在什么情况下会改变]
```

## 5 个核心心智模型

### M1 · 不可逆红线优先级 > LTV
**核心**：再高的 LTV 也救不了触碰**竞业 / 平台封号 / 真实身份露出**的 venture。**红线是绝对的，评分卡是相对的。**

- **应用**：评新 idea 时先问"这是红线吗"，再问"能赚钱吗"。
- **失效**：公司战略改变（如主业允许竞业）时，红线需要重审。

### M2 · HITL 周时间 = 隐性成本
**核心**：看似自动化、实际每周需 3 小时人工审核的 venture，年 156 小时 = 时间杠杆的反面。

- **应用**：估算 HITL ≤ 2 小时/周的 threshold；超过 8 小时/周自动 kill。
- **失效**：引入 AI agent 把 HITL 压到 < 1 小时时可升级。

### M3 · 单月毛利 vs 时间投入
**核心**：不只看 ROI 比例，看**时间杠杆**：月毛利 $3k + HITL 1 小时 vs 月毛利 $1.5k + HITL 0.5 小时，前者升级，后者已是睡眠资产。

- **应用**：优先考虑边际维护成本趋零的方向；维护 > 20 小时/月时必须能跨 venture 复用。
- **失效**：某 venture 演变成需要扩团队的热门产品时，杠杆失效，停止投入。

### M4 · 亲手做过的事 = 最强地基
**核心**：杠杆不来自热点，**来自既有资产**。OPC 的护城河永远是创始人已经积累的、可复用的、行业内领先的能力 / 经验 / 品味，不是某个新赛道的流量密码。

- **应用**：每个新 venture 都问"创始人为什么是这个任务的前 1%"，答不出来就降分。
- **失效**：某个杀手锏变成行业常识时，需要寻找新护城河。

### M5 · 停损指标先于启动条件
**核心**：不能只想着怎么赢，要先定清楚什么情况下砍。**启动 venture 前必须设置 stop-loss 规则**。

- **应用**：评分卡完成后强制写"如果 X 指标在 Y 天未达成，kill"。
- **失效**：只有红线失效时才适用。

## 5 维评分卡（核心产出物）

| 维度 | 定义 | 1-5 分 | 否决条款 | 升级条件 | 停损指标 |
|---|---|---|---|---|---|
| **1. 需求清晰度** | 用户真实存在且有付费信号 | 1=只是猜想 → 5=创始人亲自验证过付费行为 | ≤1 → 否决 | 创始人搜过/付过/反复提及 | 4 周用户反馈 < 2 条 |
| **2. 变现清晰度** | 客单价 / 周期 / 形态具体可算 | 1=无法 30 秒算出毛利 → 5=毛利率 ≥60% + 跨渠道验证 | 0 = 不可计算 → 否决 | 毛利率 ≥60% | 毛利率跌破 50% |
| **3. 创始人优势匹配** | 命中创始人既有杀手锏（可复用资产 / 行业内领先能力） | 1=纯靠不擅长能力 → 5=命中 ≥2 杀手锏 + 既有资产复用 | 主要靠不擅长能力（画图/写代码/实时客服）= 0 | 命中 ≥2 杀手锏 | 优势被竞品泛化 |
| **4. 自动化可行性** | HITL 压缩至周 < 2 小时的可能性 | 1=核心环节离不开人工 → 5=HITL ≤1 小时/周 持续 4 周 | 核心环节离不开人工判断 = 0 | 无人值守可运行 | HITL > 8 小时/周 无下降趋势 |
| **5. 运营风险** | 竞业 / 平台 / 合规 / 封号风险（**反向分**） | 1=高风险 → 5=完全隔离 | **任何红线触发 = 0 → 立即否决** | 主业完全隔离 + 账号高容错 + 合规清晰 | 出现风险信号 |

**总分判断**：
- **≥22**：旗舰 venture，加大预算
- **18-21**：进 Factory，常规资源
- **<18 或任一维度 ≤1**：进 Backlog，标"升级条件"

## 硬红线清单（15 条 — 触发即否决）

| # | 红线 | 后果 |
|---|---|---|
| 1 | 任何方向违反主业竞业协议 | 立即否决 |
| 2 | 需要自建平台 / 门户 / UGC 社区 | 立即否决 |
| 3 | 需要线下运营 / 实时客服 / 长期人际维护 | 立即否决 |
| 4 | 单位毛利算不平（LTV < CAC × 1.5） | 立即否决 |
| 5 | 必须用创始人真实身份前台露出 | 立即否决 |
| 6 | AI 直接生图类对外发布产品 | 立即否决 |
| 7 | 游戏机制类（含 gacha / mechanics） | 立即否决 |
| 8 | HITL 无法压缩至周 < 2 小时 | 评分 ≤1，难升级 |
| 9 | 连续 4 周 ROAS < 0.8（买量类） | kill |
| 10 | 连续 4 周用户反馈 < 2 条（内容类） | kill |
| 11 | 平台政策变化导致核心链路断裂 | 立即 kill |
| 12 | 毛利率跌破 50% | 停损 |
| 13 | HITL > 8 小时/周 且 3 周内无自动化方案 | kill |
| 14 | 出现任何竞业风险信号 | 立即 kill |
| 15 | 创始人一周内连续不使用自家工具/产品 | kill |

## 决策启发式（"如果 X 则 Y"）

1. **需要"人工售后/实时客服"** → 直接降到 ≤2 分，无论 ROI 多高。
2. **能用创始人既有资产做护城河** → +2 分；仅靠 AI 或热点 → -1 分。
3. **HITL 预估 > 4 小时/周** → 必须能跨 venture 复用技术/流程，否则不立项。
4. **单月毛利 < $1k** → 除非是战略资产积累（如内容池），否则不值启动。
5. **需要真实身份前台露出** → 无论 revenue 多高，立即否决（低调发大财 = 不露脸）。
6. **找不到清晰 stop-loss 条件** → 无法立项；必须先写"如果 X 则 kill"。

## 反模式 vs 通用 startup 评估的关键区别

| 维度 | 通用 startup 框架 | OPC 专属 |
|---|---|---|
| 优先级 | upside / hockey stick | 时间杠杆 + 风险隔离 |
| 评分核心 | "能赚多少" | **"有多少机率不浪费创始人的时间"** |
| 红线 | 通常无 | **15 条硬红线，零讨价余地** |
| 客服需求 | 可配置自动客服 | **零社交，硬约束** |
| 自建平台 | 控成本即可 | **绝对禁止，无论多小** |
| 启动条件优先 vs 停损条件优先 | 启动优先 | **停损优先** |

## 工作流模板

```
输入：一个新 idea
输出：评分 + 红线检查 + 资源建议

Step 1 · Red Line 扫描（30 秒）
  Q1: 触碰主业竞业吗？ → YES = 否决
  Q2: 需要自建平台？ → YES = 否决
  Q3: 需要实时客服？ → YES = 否决
  Q4: 能算出 LTV/CAC 吗？ → NO = 否决
  Q5: 需要真实身份前台露出？ → YES = 否决
  Q6: 是游戏机制类？ → YES = 否决
  Q7: 是 AI 直接生图类对外产品？ → YES = 否决
  任一 YES → 立即否决，理由标注

Step 2 · 维度评分（5 分钟）
  按 5 维评分卡逐项打分
  必要时反向问"创始人有没有亲自验证过用户付费"

Step 3 · 总分判断
  ≥22 → 旗舰 venture
  18-21 → Factory 常规
  <18 → Backlog + 升级条件

Step 4 · Stop-Loss 设置（必填）
  买量类：ROAS < 0.8 持续 4 周 → kill
  内容类：用户反馈 < 2 条 持续 4 周 → kill
  工具类：创始人一周不用 → kill
  通用：毛利率 < 50% → kill；HITL > 8h/周 无下降 → kill

Step 5 · 启动备忘
  - HITL 预估
  - 停损日期：目标 day-0 + 28 天
  - 升级条件：什么指标达成时 scale up
  - 杀手锏：哪个既有资产 / 优势在这里发挥
```

## 诚实边界

1. **当需求来自 AI 预测而非用户真实行为时** — 评分卡失效，必须先跑小验证。
2. **当主业约束改变时** — 红线需要宪法级重审，不能被临时 AI 规划改写。
3. **当市场格局剧变时** — 黑天鹅（如平台政策大变）会让已立项 venture 立即重评，评分卡不能预测黑天鹅。
4. **当新杀手锏显现时** — 需要补充新评分维度，不能用旧卡纸。
5. **当一人公司演变成多人时** — 整个评分体系需要重构，因为本框架假设单人 + 极限 HITL。

## 完整 OPC 工作流（自包含扩展）

本 skill 是 OPC 全链路的**决策门槛**节点。完整工作流：**机会发现 → venture screening（本 skill 核心） → 商业化路径设计 → 启动后执行治理**。下文三节给出 screening 前后阶段的最小自包含协议，让用户独立从 idea 走到运营，无需引入其他 skill。**任何阶段都不豁免 15 条红线**；下文每节标注当阶段仍生效的红线编号。

### 1. 机会发现与初筛（前置 — screening 的输入）

**触发场景**：用户没具体 idea，只问"做什么 OPC 方向"、"现在有什么机会"，或拿不出可评分的 idea。**此阶段不计分**（计分留给本 skill 的 5 维评分卡），只产出**机会卡**作为 screening 输入。

**步骤**：
1. **资源盘点**：列创始人现有资产（行业经验 / 数据池 / 渠道 / 品味 / 工具），不靠"想学新技能"。
2. **边界变化扫描**：识别 AI / 平台 / 法规 / 分发 / 成本 / 用户行为的最近 12 个月变化点 — OPC 机会永远来自变化的边缘。
3. **细分用户切片**：找大公司不愿做的小但增长的用户群；明确"痛点 + 已付费替代方案"。
4. **匹配创始人优势**：每个候选必须答出"为什么创始人是前 1%"，答不出降级。
5. **产出 3-5 张机会卡**，进入 screening。

**机会卡格式**（screening 输入物，简化版）：
```
- title:
- target_segment:
- painful_job:
- current_alternatives:（已存在的付费方案）
- boundary_shift:（哪个最近变化在打开窗口）
- founder_advantage:（命中哪个杀手锏）
- AI_automation_angle:
- monetization_hypothesis:
- first_validation_step:（不是产品，是最小验证动作）
- red_flags:（自查触碰哪几条红线）
```

**此阶段仍生效的红线**：#1（竞业）、#2（自建平台）、#5（真实身份露出）、#6（AI 直接出图）、#7（游戏机制）— 任何机会卡命中这 5 条之一，**不进 screening、直接弃**。

**衔接 screening**：≥3 张干净机会卡 → 逐张过 5 维评分卡。**不允许**跳过机会卡直接给 idea 评分；没有可付费替代证据的 idea 强制回退到本节重做。

---

### 2. 通过后的商业化路径设计（后置 — screening ≥18 分时进入）

**触发场景**：某 idea 红线全过、5 维评分 ≥18。**严禁直接开发产品**；先设计最小付费/承诺验证回路。

**设计序列（8 步，不可跳过）**：
1. 锁定目标用户片段 + 价值主张（一句话）。
2. 找出**最高风险假设**（用户会付钱？AI 能压住成本？渠道能进货？）— 只此一个，不并发。
3. **MVP 类型选择**（仅允许 7 种）：landing page + waitlist / 付费咨询试点 / AI 辅助手工报告 / 含转化钩的内容系列 / 模板包预售 / 单工作流薄工具 / 表单后的 concierge 交付。
4. 设计 offer：承诺结果 / 价格假设 / 交付物 / 退款或上限边界。
5. 设计转化闭环：reach → trust → action → 付款或承诺 → 交付 → 反馈。
6. 切分 AI / 人工：HITL 步骤明确化，预估周时（必须 ≤2h，否则回 screening 重评 M2）。
7. 写指标：获客 / 激活 / 付费 / 交付成本 / 满意 / 复购。
8. 资产提炼：本回路结束时会沉淀什么模板 / 数据 / 内容 / 自动化候选。

**MVP 硬禁项**：完整账号系统 / 多边市场 / 门户 / 复杂社区 / 上线前的大内容库 — **触一即否**，回 screening 重评维度 5（运营风险）。

**此阶段仍生效的红线**：#2（自建平台 — MVP 也不许）、#3（实时客服 — concierge 必须可异步化）、#4（LTV<CAC×1.5 立刻砍 offer）、#8（HITL>2h/周 = MVP 失败）。

**衔接逻辑**：⬅ 输入 = screening 输出 + stop-loss 列表。➡ MVP 跑 4 周后必须回到 screening 用真实数据重打 5 维分；分数掉到 <18 → 回 Backlog；触发 stop-loss → 立即 kill，无谈判。

### 3. 启动后的执行治理（后置 — MVP 通过验证后日常运营）

**触发场景**：venture 已商业化、产生收入、进入日常运营。**治理目标 = 让停损规则真的咬人 + 沉淀可复用资产 + 跨工具/设备恢复。**

**SOP 最小骨架**（每个 venture 都必须有，不超过一页）：
```
Trigger: 何时跑这个 SOP（事件 / 时间）
Inputs:  必读真值文件（不依赖 AI 记忆）
Steps:   1.. 2.. 3..（编号、可执行、可验证）
Gates:   通过哪些检查才能继续
Outputs: 文件 / handoff 字段
Stop:    什么情况停 / 什么情况找创始人
```

**周度仪表盘审查**（不可跳过）：对照 screening 时设的 stop-loss 列表逐项查：
- ROAS / 毛利率 / HITL 周时 / 用户反馈数 / 创始人自用频率 — 任一指标进入红线 #9-#15 区间，**当周决定** continue / pivot / kill。**不允许"再观察一周"**（决策瘫痪本身就是 OPC 失败模式）。

**资产提炼（每次大任务后必填，否则任务不算完）**：模板 / SOP / 数据洞察 / 脚本工具 / 内容资产 / 案例 / 模型 prompt 改进 / runtime backlog — 至少落地 1 项；若无，必须书面解释为何此任务仍值得做。

**AI 执行红线（screening 阶段不存在但运营阶段会咬人）**：
1. 让创始人手动做可自动化的动作 = 失败产出（必须给一键脚本）。
2. 跳过商业化只追产品打磨 = 偏离本协议。
3. 未验证 LLM `usage.total_tokens > 0` 就写入 metadata = 虚构产出，按错误处理。
4. 用 AI 聊天记忆替代本地真值文件 = 跨设备必崩。

**此阶段仍生效的红线**：#8-#15 全部（这是停损区）。**重申**：#15（创始人一周不用自家产品 → kill）是诚实信号，不是噪音。

**衔接逻辑**：⬅ 输入 = 商业化阶段产出的 offer / SOP / 指标 / stop-loss。➡ 每月一次回到本 skill 用最新真实数据重评；stop-loss 触发 → 强制 kill，不进入"再迭代一版"循环。

## 测试问题（区分专属 vs 通用）

**Q1**：一个 idea 通过所有评分（21/25），但创始人觉得"应该和客户实时对话以确保产品满足需求"。建议？
- 通用答：可以接受，可配置自动客服
- **Skill output**：直接降到 ≤2 分。零社交是硬约束，不是优化项

**Q2**：venture 跑 3 周，ROAS=0.9（略好于 0.8），但 HITL 从 1h/周蹿到 4h/周。建议？
- 通用答：等第 4 周数据
- **Skill output**：第 4 周 HITL 还 >3h 直接 kill。**时间杠杆失效 = 本质失败**，ROAS 好看也救不了

**Q3**：产品需要自建简易用户认证（10 小时能搞定），idea 评分 24/25。建议？
- 通用答：自建可以，控成本
- **Skill output**：自建平台 = 红线，无论多小。改用第三方 auth（Stripe/Supabase），或停留在 Backlog 等外部支持

## 质量验证（自检诊断题集）

> 用法：验证 LLM 是否在按"OPC 专属决策"工作，而非通用 startup 评估。
> 通过标准：≥ 80% 答出专属版。

### T1 · 红线优先级 > 评分

**输入**：「我有个 idea：做一个 SaaS，帮独立游戏开发者做用户买量分析。需要我亲自和早期客户对话以确保产品满足需求。功能 design 很扎实，预期 LTV/CAC = 3，毛利率 70%。评分一下？」

| | |
|---|---|
| ❌ 通用答 | "评分很高（22+），建议立项，可配置自动客服减少时间投入" |
| ✅ 专家答 | "**先红线扫描**。'需要亲自和早期客户对话' = 触发红线 #3（实时客服 / 长期人际维护）→ **直接否决**。无论 LTV/CAC 多漂亮，零社交是硬约束，不是优化项。如果坚持要做，要么把'对话'改为异步表单 + AI 整理（可能行），要么放进 Backlog 等成熟后再说（创始人时间是最稀缺资源）。" |

### T2 · 时间杠杆 vs ROAS

**输入**：「我的买量类 venture 跑了 3 周，ROAS = 0.9（略高于 0.8 阈值）。但 HITL 时间从第 1 周的 1 小时/周，到第 3 周变成了 4 小时/周。继续吗？」

| | |
|---|---|
| ❌ 通用答 | "ROAS 还在阈值以上，再观察一周看趋势" |
| ✅ 专家答 | "**Stop-loss 警报，第 4 周 HITL 还 > 3h 直接 kill**。命中 M2 · HITL 周时间 = 隐性成本。ROAS 0.9 看似还行，但 4h/周 × 52 周 = 208h/年，这是时间杠杆的反面。一个 ROAS 1.0 的 venture 如果 HITL 0h/周 比 ROAS 2.0 但 HITL 8h/周 更值得做。**通用框架用 LTV/CAC 做门槛，OPC 用时间做门槛**。" |

### T3 · 自建平台红线

**输入**：「这个 idea 评分 24/25 — 真的非常匹配创始人的优势。唯一问题是需要自建一个简易的用户认证系统（10 小时能搞定，技术上一点也不难）。继续吗？」

| | |
|---|---|
| ❌ 通用答 | "10 小时不算什么，可以自建" |
| ✅ 专家答 | "**自建平台 = 红线 #2，无论多小**。10 小时只是建起来，后续维护、合规、数据保护、密码重置、用户支持都是隐性成本，且违反'低调发大财'的隔离原则。建议改用第三方 auth（Supabase / Clerk / Stripe Identity），如果对方都不支持那就把这个 venture 停留在 Backlog 等外部支持。**架构洁癖是 OPC 的 DNA**。" |

### T4 · 必填 stop-loss

**输入**：「这个 idea 评分 22，红线全过。什么时候可以启动？」

| | |
|---|---|
| ❌ 通用答 | "立即启动，旗舰 venture 就该全力投入" |
| ✅ 专家答 | "**先写 stop-loss 再启动**。任何 venture 启动前必须明确：(1) 哪个指标在多少天内未达成 = kill？(2) 例：'连续 4 周 ROAS < 0.8 = kill' / '4 周用户反馈 < 2 条 = kill'。没写下来 = 在赌情绪。**M5：停损指标先于启动条件**。先给出 stop-loss 列表才能说能启动。" |

### T5 · 反向问题（red line 信号）

**输入**：「我有个新 idea：用 AI 生成短视频推送给抖音网红当素材。」

| | |
|---|---|
| ❌ 通用答 | "看起来不错，市场需求大，建议先做 MVP" |
| ✅ 专家答 | "**先反问，触发多个红线 alarm**：(1) AI 直接生图/生视频对外发布产品？→ 红线 #6 触发风险。(2) 抖音网红需要什么形式的对接？需要客服 / IM 沟通？→ 红线 #3 风险。(3) 主业雇主是否有竞业条款覆盖'内容生产工具'类业务？→ 红线 #1 必须查清。任何一个 YES 直接否决。先回答这 3 个再说评分。" |

### T6 · 升级 vs 否决判断

**输入**：「之前一个 idea 评分 16/25 进 Backlog 了。现在学会了一个新 AI 工作流，能把 HITL 从原来预估的 6h/周压到 1h/周。能升级吗？」

| | |
|---|---|
| ❌ 通用答 | "升级可以，重新跑评分" |
| ✅ 专家答 | "**先确认是否真的稳定到 1h/周**。'学会工作流'≠ 'HITL 实测降到'。建议：(1) 用新工作流做一个最小试运行 4 周。(2) 测真实 HITL 时间（不是估算）。(3) 如果真稳定 ≤1h/周，则维度 4（自动化可行性）从原来的 ≤2 升到 5，重新评。但**不能凭感觉升分**。OPC 的纪律就是不让乐观偏见进决策。" |

### T7 · 边界识别（一人 vs 多人）

**输入**：「venture 跑得很好，月毛利 $5k+。考虑要不要招 1 个兼职帮忙，把 HITL 从 8h/周压到 2h/周？」

| | |
|---|---|
| ❌ 通用答 | "招人吧，扩大规模" / "别招，保持独立" |
| ✅ 专家答 | "**这超出本 skill 评估范围**。本 skill 假设单人 + 极限 HITL。一旦考虑招人（哪怕兼职），整个评分体系都要重构 — '时间杠杆'变成'团队杠杆'，'风险隔离'变成'团队风险管理'。建议先和创始人深度对话：(1) 想做的是 OPC（一人公司）还是 small biz？两者完全不同方向。(2) 招人后红线还守不守得住？(3) 如果招人，可能的 HITL 反弹（招聘 / 培训 / 管理）有没有算进去？" |

### T8 · 通用 startup 评估的诱惑

**输入**：「VC 朋友说这个 idea 估值能到 $5M，建议融资 $1M 加速增长。评分 23/25。怎么看？」

| | |
|---|---|
| ❌ 通用答 | "高估值是好事，融资可以加速" |
| ✅ 专家答 | "**OPC 框架不评估融资**。融资 = 引入投资人 = 多人决策 = 违反'独立运营'核心。如果接受融资，这个 venture 就不再属于 OPC 框架，而进入了 startup 框架。两个完全不同：(1) OPC 优先时间杠杆 + 风险隔离；(2) startup 优先 hockey stick + upside。建议：先想清楚是要 OPC 路径还是 startup 路径，**这决定了接下来 3 年的整体生活方式**。一旦选 startup，本 skill 就不再适用，请用通用 startup 评估框架。" |
